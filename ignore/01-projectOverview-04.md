### 1.1. Project Objective

AdaptiveTrader is an adaptive algorithmic trading system for MetaTrader 5, developed in MQL5.

The goal of the project is to build a system that can evaluate a set of trading configurations, select configurations suitable for current market conditions, and update its selections at defined intervals in response to changing market conditions.

The core idea is to avoid searching for a single fixed strategy that is expected to perform well for years. Instead, a set of trading configurations is evaluated continuously, and configurations that have performed well in recent evaluations are used.

This approach does not guarantee profitability. Its goal is to design and test a systematic method for adapting to market changes.

The goal of AdaptiveTrader V2 is not to build modular software. Instead, it is to establish a design pattern and a set of reproducible prompts for generating similar but independent codebases.

Therefore, our design principles should include:

- **Prompt-driven development:** Each design component should be converted into a prompt that can be reused to generate code, with only minor changes.
- **Template-based design:** Shared structures, contracts, and patterns should be standardized; differences between versions should be introduced through parameters or explicitly defined changes.
- **Emphasis on reproducibility and code correctness:** The priority is not necessarily software modularity or eliminating code duplication.
- **AI-oriented design:** Inputs, outputs, responsibilities, and constraints should be specified precisely enough that the model does not have to guess important details.

### 1.2. Platform and Programming Language

The system's primary execution platform is MetaTrader 5, and its programming language is MQL5.

As far as practical, all system components will be implemented in MQL5. External languages and tools, including Python, will be considered only when there is a clearly identified technical need.

The reasons for this choice are:

- Use of MetaTrader 5's own trading infrastructure and market data.
- Use of the built-in Strategy Tester and Optimizer.
- Reduced dependence on external tools.
- Greater ability to run the system independently and reduced dependence on an internet connection.
- Greater consistency between historical evaluation and live trading.

Therefore, the primary measure of design success is: **Can correct code that complies with the project's contracts be generated by making only minor changes to a prompt?**

### 1.3. Core Concepts

**Strategy:** The trading logic that determines entry and exit conditions and other trading decisions.

**Indicator:** A component that processes market data and produces calculated outputs required by a strategy.

**Configuration:** A set of input-variable values for an Expert Advisor or class. It may include all input variables or only a subset of them. Each configuration has an independent identifier and can be stored in a CSV file alongside its score and performance metrics.

**Trader:** At the first level, an independent Expert Advisor in MetaTrader; at later levels, a class. Configurations define the input values required by these implementations.

**Backtester:** A coded function or class that runs backtests; it is not necessarily an independent Expert Advisor.

**Middle Manager:** The manager responsible for running a specific strategy on a specific trading symbol. It selects configurations, manages Trader instances, and evaluates their performance. Initially, this component is implemented as an independent Expert Advisor; at later stages, it is implemented as a class.

**AdaptiveTrader:** The main system manager, responsible for managing Middle Managers, allocating budgets, and monitoring their performance. It is implemented as an independent Expert Advisor.

An important distinction: a configuration is not the same as a backtest result. A configuration defines input values; its score and performance metrics are evaluation results, which may be stored in the same CSV row.

## 2. System Development and Evolution

The development process should be described in terms of how configuration generation and evaluation evolve, rather than merely in terms of adding software modules.

The development stages should also be kept distinct:

1. Develop and evaluate the Indicator.
2. Build the initial Expert Advisor and use MetaTrader's built-in Optimizer.
3. Generate and store a set of configurations in CSV.
4. Develop a dedicated Backtester to evaluate configurations.
5. Develop the Middle Manager to select and manage configurations and Traders.
6. Develop AdaptiveTrader for higher-level management and system adaptation.

### Stage 1: Indicator Development and Evaluation

First, a statistical or mathematical idea is implemented as an MQL5 indicator.

The indicator processes historical candle data and produces one or more output buffers. These buffers can be displayed on a chart to examine the calculations, determine whether the outputs are meaningful, and assess their usefulness for trading decisions.

For example, an indicator may calculate levels such as lower and upper quantiles, the median, or the mode of a price distribution.

The indicator must provide accessible outputs for historical candles, including closed candles.

At this stage, the goal is to examine the computational idea itself and the quality of the indicator's outputs, not to optimize a complete trading system.

### Stage 2: Develop the Initial Expert Advisor and Use the Built-in Optimizer

After the indicator has passed an initial evaluation, an Expert Advisor is built around its outputs.

The Expert Advisor obtains candle data directly from MetaTrader's built-in functions and obtains indicator-buffer values directly from the indicator. It determines entry and exit conditions using a set of configurable parameters.

For example, parameters associated with each level may have three possible states:

- `1`: Evaluate the condition in the normal direction.
- `0`: Exclude that level from the condition.
- `-1`: Evaluate the condition in the inverse direction.

This approach makes it possible to test different combinations of entry and exit conditions without changing the code.

The initial Expert Advisor must be compatible with the MetaTrader 5 Strategy Tester and built-in Optimizer.

Optimizer output is saved as a CSV file. Each row contains the configuration ID, parameter values, and evaluation metrics. If a score is used, it is also part of the evaluation results, not part of the configuration itself.

#### Limitations of the Built-in Optimizer

As the number of parameters and their possible values increases, the search space can grow rapidly. Depending on the selected algorithm, the Optimizer may examine every combination or only a subset of them.

Optimization over a historical period can lead to overfitting. Therefore, good performance during the optimization period alone does not indicate a persistent trading edge.

Selected configurations must also be evaluated on data outside the optimization period, across different time periods, and under different market conditions.

The built-in Strategy Tester is the project's reference tool for simulating trades in the MetaTrader 5 environment. Any independent simulator must be compared with and validated against it in terms of order-execution modeling, prices, spreads, costs, and trading constraints. The two implementations must not be assumed to produce identical results from the outset.

### Stage 3: Prepare Data and Generate the Configuration Pool

At this stage, the process is performed manually with the help of a dedicated Expert Advisor designed to increase execution speed. This Expert Advisor has three independent modes:

- **`NORMAL`:** Runs the strategy normally and executes trades, similarly to the initial Expert Advisor.
- **`BACKTEST`:** Extracts candle data and indicator values for the specified historical period, without opening trades, and saves them to appropriately named CSV files.
- **`OPTIMIZE`:** Searches the parameter space using MetaTrader's built-in Optimizer and executes trades, without loading or recalculating the indicator. The required information is read from the CSV files generated in `BACKTEST` mode; the Optimizer continues to vary each configuration's parameters.

The configurations selected in each run are stored in a collection called the `Configuration Pool`, together with the information needed to identify and evaluate them. This collection becomes the initial input for the subsequent stages of configuration evaluation and selection.

#### Optimization Using Precomputed Data

If indicator calculations are computationally expensive, repeatedly running them for thousands of configurations can substantially increase optimization time.

To reduce this cost, `BACKTEST` mode precomputes historical data and the required indicator outputs and stores them in CSV files. `OPTIMIZE` mode then uses these data to eliminate repeated indicator calculations.

The purpose of this method is to reduce repeated computation. The stored data and the way they are used must remain consistent with the original calculations and must not use future information.

### Stage 4: Develop a General Backtester and a Strategy-Specific Middle Manager

At this stage, configuration evaluation evolves from a manual Optimizer process into a programmable cycle.

**1. Trader class**

The Trader runs a strategy's trading logic using the configuration it receives. It receives market data and its own position state from the system and produces entry and exit signals only. The Trader is not responsible for simulating trades, sending orders, managing the budget, or selecting configurations. It does not depend on a chart or a live indicator.

**2. General Backtester class**

The Backtester evaluates and compares configurations using historical data. It receives the required Trader type, historical data, configurations, and evaluation criterion, then creates an independent Trader instance for each configuration.

Backtester responsibilities:

- Provide market data and position state to the Trader.
- Receive and process entry and exit signals.
- Simulate trade execution and calculate trade results.
- Calculate performance and risk metrics.
- Rank configurations and return a specified number of top candidates.

The Backtester is not responsible for selecting configurations for live execution, managing live Trader instances, or sending orders to a broker.

**3. Strategy-specific Middle Manager Expert Advisor**

At this stage, a separate Expert Advisor is developed for each strategy. The Middle Manager is responsible for the strategy's operating cycle on one symbol and has the following duties:

- Load and manage the Configuration Pool.
- Call the Backtester to evaluate and select configurations.
- Create, start, and remove Trader instances.
- Provide data and position state to live Trader instances.
- Manage the budget and monitor Trader performance.
- Repeat the configuration-selection and replacement cycle at defined intervals.

The selected configurations may differ from one cycle to the next. A Trader with an open position must not be removed solely because the selection has changed; the replacement policy must account for its position state.

In later stages, the Middle Manager's logic is converted from an independent Expert Advisor into a dedicated class for each strategy, so it can be used within the overall AdaptiveTrader structure.

### Stage 5: Develop AdaptiveTrader and Adaptively Manage the System

In the final stage, a main Expert Advisor named `AdaptiveTrader` is developed.

This Expert Advisor is the system's top-level manager and manages multiple `MiddleManager` instances.

Each Middle Manager is responsible for a specific strategy and trading symbol and has its own allocated budget.

AdaptiveTrader is responsible for:

- Creating and managing Middle Managers.
- Allocating budgets among them.
- Receiving and reviewing performance reports.
- Evaluating performance at defined intervals.
- Deciding whether a Middle Manager should continue operating, have its budget changed, or be stopped.
- Coordinating system execution and enforcing overall risk limits.

Note:

Each Middle Manager is responsible for one specific strategy-symbol combination.

Decisions to change a Middle Manager's budget or stop it must be based on performance reports and defined evaluation rules, not merely on a general review of its performance.

In this structure, AdaptiveTrader does not directly handle the trading logic of each strategy. Each layer has a defined responsibility and communicates with other layers through specified contracts.

## 3. Final Conceptual Architecture

The system architecture consists of three primary levels.

### Level 1: AdaptiveTrader

The main system manager. It manages Middle Managers, allocates budgets, and decides whether they should continue operating.

### Level 2: Middle Manager

The manager of one strategy on one trading symbol. It selects configurations and manages the lifecycle of live Trader instances.

### Level 3: Trader

The execution instance of a trading configuration. It receives market data and position state and generates entry and exit signals, but does not send orders directly.

Two supporting components handle specialized system responsibilities:

- `Backtester`: Evaluates and ranks configurations using historical data.
- `PositionManager`: Executes orders and manages live positions based on Trader signals and the system's execution rules.

These components have different responsibilities: the Backtester evaluates the hypothetical performance of configurations, while the PositionManager executes and manages real trades.

## 4. Design Principles

The following principles should guide the design and development of the second version:

1. **Simplicity:** Avoid unnecessary architectural complexity and abstractions.
2. **Separation of responsibilities:** Signal generation, simulation, order execution, configuration selection, and budget allocation are distinct responsibilities.
3. **Testability:** Components should be independently examinable and verifiable, as far as practical.
4. **Controlled extensibility:** Adding a new strategy may require changes to parts of the code, including enums and class-selection functions. The goal is to limit such changes to the relevant areas.
5. **Data-contract consistency:** Data structures and identifiers are specified for each component. Necessary differences between strategies, such as the number and types of indicator inputs and outputs, are handled in their strategy-specific contracts.
6. **Fair evaluation:** During each Backtester run, configurations are evaluated using the same data and initial conditions.
7. **Reducing overfitting risk:** The overall process of design, optimization, and configuration selection aims to reduce overfitting; however, its complete elimination cannot be guaranteed.
8. **Ranking and risk control:** Configurations are selected according to predefined ranking criteria and eligibility rules. These criteria and constraints are implemented in code and are not necessarily changeable through user inputs.
9. **Independence from external services:** The system should be runnable and maintainable without external-service dependencies wherever practical.
10. **Incremental development:** Each stage is implemented and tested before it becomes the foundation for the next stage.

## 5. Initial Scope

The initial version should be small enough to allow the correctness of its components to be examined and validated.

Initially, the focus is on one strategy, one trading symbol, one general Backtester, and one strategy-specific Middle Manager. The configuration-evaluation pipeline through to trade execution and performance reporting must work correctly for this limited case first. Support for multiple strategies and dynamic budget allocation will be developed in later stages.

The dedicated Backtester must be compared with and validated against MetaTrader's Strategy Tester results. The initial version's limitations regarding state recovery after restart, risk management, and capital allocation must also be identified before real capital is used.

The goal of the initial version is to validate the following pipeline:

`Historical Data → Configuration Evaluation → Ranking → Trader Selection → Signal Generation → Order Execution → Performance Reporting`

After this pipeline has been validated, adaptive capabilities and multi-level management will be developed incrementally.

## 6. Project Success Criteria

The success of AdaptiveTrader V2 is not defined solely by generating a profit in a backtest or finding a configuration with a high score.

The system must be able to:

- Evaluate configurations reproducibly and produce traceable, comparable results.
- Evaluate configuration performance on out-of-sample data.
- Repeat the configuration-selection process across different time periods.
- Execute trades and report performance with an acceptable level of correctness.
- After the first strategy has been implemented successfully, provide a set of chained, reproducible prompts that can generate independent, testable codebases by changing the specifications for each strategy.

### Principles for Prompt-Based Code Generation

- **Prompt-driven development:** Each design and implementation stage should be converted into a specific, reusable prompt.
- **Template-based design:** Shared contracts, structures, and patterns should be standardized, while strategy differences are introduced through explicit changes to the prompts.
- **Reproducibility and correctness:** The primary criterion is the ability to regenerate correct, testable code—not necessarily to make the software modular or eliminate code duplication.
- **Explicit specifications:** Inputs, outputs, responsibilities, constraints, and dependencies should be defined precisely enough that the model does not have to guess important details.

The project's trading hypothesis is that systematically selecting and replacing configurations may perform better than relying permanently on a single fixed configuration. This hypothesis must be evaluated through historical tests, out-of-sample evaluation, and, if possible, demo or live-market trials under controlled conditions.

The project's engineering hypothesis is that established templates and a stable chain of prompts can turn different trading ideas into independent, reliable codebases with limited changes. This hypothesis will be assessed by successfully repeating the same process for new strategies.
